# Security and Operations

## Required migration

Before deploying the hardened booking code, review and apply:

`supabase/migrations/202608090001_booking_security_hardening.sql`

Apply it to a staging project first, then production from the Supabase SQL editor after taking a current backup. The migration is additive: it adds idempotency and authoritative tour fields, database-backed rate limiting, non-negative amount constraints for new/updated rows, a conditional one-payment-per-booking index, and transactional booking/status functions. It does not delete existing bookings, customers, payments, or references.

If existing bookings contain duplicate payments, the unique payment index is intentionally skipped and Supabase emits a notice. Review those rows manually; do not delete or merge them without owner approval.

## Rate limits

The code uses the database limiter after the migration is installed and an instance-local fallback if it is temporarily unavailable:

- Admin login: 5 attempts per 15 minutes per opaque client key.
- Booking creation: 6 attempts per 10 minutes.
- Booking status: 12 attempts per 10 minutes.
- Authenticated admin mutations: 60 attempts per 10 minutes.

Client addresses are HMAC-hashed before storage. Set `RATE_LIMIT_SECRET` to a long random server-only value. If it is absent, `ADMIN_SESSION_SECRET` is used. Vercel's injected forwarding header is preferred; generic forwarding headers are accepted only outside production.

## Admin sessions

Admin sessions are HMAC-signed, contain issued-at and expiry times, expire after eight hours, and use HttpOnly, SameSite=Lax cookies with Secure enabled in production. Rotating `ADMIN_SESSION_SECRET` invalidates every existing session. `ADMIN_PASSWORD` and `ADMIN_SESSION_SECRET` must be independent long random values.

## Uploads and bookings

- Screenshots are limited to 5 MB.
- PNG and JPEG magic bytes are validated; browser MIME and filenames are not trusted.
- Extensions and storage paths are generated by the server.
- The bucket remains private.
- Tour identity, schedule, departure city, price tier, price, and payment method come from server-owned data.
- A client submission UUID provides idempotency.
- Customer, booking, and payment rows are created in one database transaction.
- A failed database transaction triggers best-effort removal of the newly uploaded object.
- Existing references remain valid; only new references use the opaque cryptographic format.

## Owner decisions still required

- Payment/deposit policy beyond the confirmed workflow.
- Child pricing.
- Provenance and publication permission for named customer testimonials.
- Review of any existing duplicate payment rows reported by the migration.

No business rule has been guessed for these items.
